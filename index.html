The definition

What is
SASE?

Secure Access Service Edge is an architecture that delivers network connectivity and network security as one service, governed by a single policy that follows the identity rather than the location. The term was introduced by Gartner in 2019 to describe the convergence that had already begun in practice.

SASE combines wide-area networking with security enforcement so that a user in a branch office, a contractor on a home connection, and a workload in a public cloud are all governed by the same set of rules — evaluated at an enforcement point close to them, rather than by routing their traffic back to a data center first.

01

What it brings together

SASE converges the networking layer — SD-WAN, routing, and WAN optimization — with the security layer that had been sold separately: firewalling, secure web access, zero trust network access, cloud application control, DNS filtering, and data protection. The convergence is the point. Running them as one system means a policy is written once and evaluated once, instead of being restated in each console and drifting apart over time.

02

What it protects

The scope is everything that now sits outside the old perimeter: remote and hybrid employees, branch offices, cloud workloads and the applications running in them, private applications that used to sit behind a VPN, third-party contractors, and the devices that cannot run an agent at all — IoT sensors, medical equipment, industrial controllers, and legacy systems that will never be patched again.

03

The problem it solves

The perimeter model assumed users, applications, and data sat inside one building. When applications moved to SaaS and users moved everywhere, backhauling traffic to a central inspection point added latency to every request and left branch and remote traffic either slow or uninspected. Meanwhile the security stack fragmented across appliances and consoles, each with its own policy language — so the same rule had to be written several times and verified nowhere.

04

Where enforcement runs

SASE describes what converges, not where the hardware lives. Many vendors deliver enforcement exclusively from their own cloud points of presence, which requires routing traffic through their infrastructure. That is one implementation, not the definition. Inspection can equally run on-premises, at the branch edge, or in infrastructure the organization controls — which matters when data residency, latency, or sovereignty requirements make a vendor-operated cloud the wrong place for traffic to be decrypted.

SASE is frequently discussed alongside SSE — Security Service Edge — which refers to the security half of the model on its own: secure web access, cloud application control, and zero trust network access, without the networking layer. An SSE deployment is a common first phase on the way to SASE.

What is SASE Deployment?

SASE deployment is a phased adoption program that replaces fragmented network and security controls with one SASE policy plane across users, branches, and cloud edges.

A SASE architecture is delivered through SASE implementation, SASE migration, and SASE optimization rather than through a single overnight cutover.

SASE deployment is an operating-model change rather than a one-time appliance swap.

Its function is to bind SD-WAN or local routing and SSE controls such as ZTNA, SWG, CASB, and FWaaS to one identity-sourced policy.

Its scope includes remote users, branch sites, data centers, and public-cloud workloads that still terminate on VPN concentrators or stacked proxies.

Gartner introduced SASE in 2019 as the convergence of networking and security as a cloud-delivered service; SASE Solutions maps those components, uses, benefits, challenges, and practices.

Its measurable outcome is fewer policy consoles and a documented path from assessment through design, SASE migration, and optimization.

Once that definition is fixed, the next decision is which SASE deployment model will carry the rollout: single-vendor, dual-vendor, or managed SASE.

What are the SASE Deployment Models?

SASE deployment models are the three contracting patterns used to source and operate SASE during a SASE architecture rollout: single-vendor SASE, dual-vendor SASE, and managed SASE.

Each SASE deployment model changes who owns the policy engine, the points of presence, and day-2 operations during SASE implementation.

Single-vendor SASE is a SASE deployment model in which one vendor supplies both the networking fabric and the SSE stack. It reduces SASE implementation integration because one policy engine covers ZTNA, SWG, CASB, and FWaaS. Gartner treats a capable single-vendor SASE platform as the preferred long-term pattern when point-of-presence coverage is sufficient.

Dual-vendor SASE is a SASE deployment model that pairs a networking vendor with a separate SSE vendor. It lets a team keep an existing SD-WAN fabric while adding SASE security controls during SASE migration. The integration contract must name identity, logging, and failover so the two planes do not drift.

Managed SASE is a SASE deployment model operated by a partner that owns day-2 policy, telemetry, and incident response. It is used when the internal team cannot staff 24x7 change control for SASE. A managed security service provider typically runs onboarding against a named service-level agreement.

Each model still has to be understood on its own terms, starting with single-vendor SASE deployment.

What is Single-Vendor SASE Deployment?

Single-Vendor SASE deployment is a SASE contracting model that sources networking and SSE from one vendor so one policy engine governs the SASE architecture.

This model is chosen during SASE deployment when one platform can cover ZTNA, SWG, CASB, FWaaS, and the required points of presence without a second SSE contract.

It is a single commercial and operational stack rather than a stitched pair of products.

Its function is to compile identity-bound policy once and distribute that compiled policy to every edge.

Its scope is the set of users, branches, and cloud edges that the vendor point-of-presence map can actually reach.

Its mechanism is one console, one log schema, and one failover path, which removes dual-vendor correlation work.

Gartner single-vendor SASE evaluations treat feature completeness and point-of-presence density as the gate for this model.

When one vendor cannot cover networking and SSE together, dual-vendor SASE deployment is the alternative model.

What is Dual-Vendor SASE Deployment?

Dual-Vendor SASE deployment is a SASE contracting model that splits networking and SSE across two vendors during SASE implementation.

This model is used in SASE deployment when an existing SD-WAN estate must stay in place while SSE is added as the security service edge.

It is a two-contract architecture.

Its function is to keep the current routing fabric while SASE security controls (ZTNA, SWG, CASB, FWaaS) attach through identity and traffic steering.

Its scope is any estate where the networking vendor and the SSE vendor both have production coverage for the same users and sites.

Its mechanism is a written interface for identity assertions, session logs, and failover so policy does not diverge between planes.

Its risk is silent drift: a route change that bypasses an SSE inspection point during SASE migration.

If the internal team cannot operate either plane at 24x7, managed SASE deployment becomes the operating choice.

What is Managed SASE Deployment?

Managed SASE deployment is a SASE operating model in which a partner runs day-2 operations of the SASE architecture.

This model is selected during SASE deployment when the customer owns policy intent but cannot staff 24x7 onboarding, change control, and incident response.

It is an outsourced operations overlay on a single-vendor or dual-vendor SASE stack.

Its function is to execute SASE implementation tasks (connector install, identity sync, policy publish, and telemetry watch) against a named service-level agreement.

Its scope includes user onboarding, site cutover, TLS exclusion maintenance, and ticketed policy changes.

An MSSP is the usual operator for this model, with delegated administration in the SASE console.

Its measurable outcome is a documented RACI for who may change SASE policy and how fast a blocked session is investigated.

Once the model is chosen, SASE deployment moves from contracting into the ordered steps that actually roll out the architecture.

How to Assess Readiness for SASE Deployment?

Assessing readiness for SASE deployment consists of 6 steps that produce a written inventory of identity, traffic, and controls before SASE implementation starts.

This assessment is the first phase of SASE deployment, and it decides whether SASE migration can begin on a named user group.

  1. Inventory the identity sources, groups, and device-posture signals so SASE deployment has an authoritative user and device map before design starts.
  2. Map every branch, data-center, and cloud traffic path so SASE implementation knows which flows still backhaul through a VPN concentrator.
  3. List current firewalls, web proxies, CASB tools, and ZTNA pilots so SASE rollout can name what will be kept, replaced, or run in parallel.
  4. Record every application that cannot accept an agent so SASE migration can plan network-based enforcement for those remaining agentless workloads.
  5. Set written pass criteria for latency, policy coverage, and console count so SASE deployment success is measurable after each wave.
  6. Validate readiness by publishing the inventory, the retire list, and the first-wave user group to the owners who will approve SASE implementation.

With readiness recorded, SASE deployment continues by defining the security and network policies the architecture will enforce.

How to Define Security and Network Policies for SASE?

Defining security and network policies for SASE consists of 6 steps that turn inventory into one identity-bound policy language before SASE deployment cuts over traffic.

This design phase of SASE deployment is where SASE implementation either stays consistent or splits back into per-product dialects.

  1. Write every access policy in identity, application, and posture terms so SASE deployment does not encode office subnets as trust.
  2. Classify each in-scope application by sensitivity so SASE implementation can apply ZTNA, step-up, or block actions from one rule set.
  3. Define TLS inspection scope and named exclusions so SASE rollout can inspect encrypted threats without scanning health or finance destinations.
  4. Set routing intent per application class so SASE migration sends voice, SaaS, and bulk backup onto paths that match their latency needs.
  5. Name the change process and the named approvers so SASE deployment has one path from written intent to published policy.
  6. Validate the policy pack by replaying it against the readiness inventory and confirming every in-scope application has an owner and an action.

Once policy is written, SASE deployment must choose the vendor that can enforce that policy at the required edges.

How to Choose a SASE Vendor for Deployment?

Choosing a SASE vendor for deployment consists of 6 steps that test coverage, architecture, and operations against the policy pack produced for SASE deployment.

Vendor selection is the SASE implementation gate that decides single-vendor, dual-vendor, or managed SASE for the SASE architecture rollout.

  1. Score native ZTNA, SWG, CASB, and FWaaS coverage so SASE deployment does not depend on a resold or roadmapped control.
  2. Test identity integration with the production IdP so SASE implementation can resolve groups and posture before the first user session.
  3. Measure point-of-presence reach and TLS-on latency for representative user sites so the SASE rollout has numeric pass criteria written down.
  4. Inspect where user traffic is decrypted, logged, and stored so SASE migration can satisfy jurisdiction rules and data retention requirements.
  5. Run a proof of concept on the first-wave user group so SASE deployment evidence comes from production-like traffic, not a lab.
  6. Validate the choice by recording coverage, latency, and operations scores against the written pass criteria and naming the selected model.

After the vendor is named, SASE deployment moves into SASE migration of the existing infrastructure.

How to Migrate Existing Infrastructure to SASE?

Migrating existing infrastructure to SASE consists of 6 steps that move users and sites from VPN and appliance paths onto the SASE architecture in waves.

This SASE migration is the execution phase of SASE deployment, and it is sequenced so a failed wave can be reversed without a global outage.

  1. Stand up the first enforcement point beside the current stack so SASE deployment can observe live traffic before it enforces.
  2. Connect the identity provider and synchronize groups so SASE implementation issues access decisions from the same source as the rest of the estate.
  3. Move one user group in monitor-only mode so SASE rollout can compare logs against the current VPN path before enforcement is switched on.
  4. Cut that group to enforce, then expand site by site so SASE migration never converts the whole estate in one change window.
  5. Retire unused VPN concentrators and duplicate proxies after each wave so SASE deployment removes the path users could fall back to.
  6. Validate the wave by confirming policy coverage, session success, and latency against the assessment budget; use SASE vs VPN as the comparison frame for the path being replaced.

Migration only holds if the prerequisites for SASE deployment were in place before the first wave, which is the next heading.

What are the Prerequisites for SASE Deployment?

Prerequisites for SASE deployment are the three foundations that must exist before a SASE architecture can be implemented: an identity provider, a network inventory, and a policy framework.

SASE deployment stalls when any one of these three is missing, because SASE implementation has no user map, no traffic map, or no intent to compile.

An Identity Provider is the directory and authentication system that issues the user, group, and device claims SASE policy consumes. It is the control-plane input for SASE deployment, because ZTNA and posture decisions cannot be written in subnets. Typical sources are Microsoft Entra ID, Okta, or an equivalent SAML or OIDC issuer already used for SaaS.

Network inventory is the recorded list of sites, circuits, VPN concentrators, firewalls, and application paths in the current estate. It tells SASE deployment which flows to migrate and which appliances to retire. Without it, SASE migration cannot name a first-wave site or a fallback path.

Policy framework is the written language of identity, application, and inspection intent that the SASE engine will compile. It is the design artifact SASE implementation publishes to every edge. A framework that still speaks only in VLAN and port numbers will recreate the perimeter inside the SASE console.

Even with those prerequisites in place, SASE deployment still hits a short list of common challenges, which is the next heading.

What are Common SASE Deployment Challenges?

Common SASE deployment challenges are the three failure modes that stall a SASE architecture rollout: legacy integration, policy complexity, and change management.

Each challenge appears during SASE implementation when the new policy plane meets the estate that SASE migration is supposed to replace.

Legacy integration is the work of attaching SASE to VPN concentrators, stacked proxies, and agentless devices that cannot be cut over on day one. It matters in SASE deployment because a dual-path estate will route around inspection if steering is incomplete. A typical case is a plant controller that must stay on network-based enforcement while laptops move to ZTNA.

Policy complexity is the translation of years of firewall, proxy, and VPN rules into one identity-bound SASE language. It is the design risk in SASE implementation: copied rules recreate contradictions in the new console. Teams that rebuild intent from applications, rather than importing every ACE, finish SASE migration with a shorter, auditable set.

Change management is the operating process that decides who may publish SASE policy and how users are told about path changes. It is the people risk in SASE deployment, because a technically correct cutover still fails if help desks cannot explain a new access prompt. A named RACI and a first-wave communications plan are the usual controls.

Those three challenges are predictable, and the next section lists how to overcome SASE deployment challenges in order.

How to Overcome SASE Deployment Challenges?

Overcoming SASE deployment challenges consists of 6 steps that remove dual paths, shrink policy, and lock change control before SASE migration expands.

This remediation is part of SASE deployment, not a side project, because unfixed legacy paths will undo SASE implementation gains.

  1. Keep the first wave in monitor-then-enforce mode so SASE deployment finds steering gaps before users lose a working access path.
  2. Rebuild policy from identity and applications rather than importing every legacy rule so SASE implementation does not copy hidden contradictions.
  3. Assign a single change owner and a fixed publish window so SASE rollout does not accept unreviewed policy edits from operators.
  4. Provide help-desk scripts and a named exception path so SASE migration tickets do not recreate standing VPN exceptions after cutover.
  5. Retire the old path after each successful wave so SASE deployment cannot fall back to an uninspected legacy VPN concentrator.
  6. Validate the fix by confirming no production session still uses a retired VPN or proxy, and that policy change lead time matches the published window.

Two planning questions sit inside that remediation: how long SASE deployment takes, and whether SASE should be deployed all at once or in phases.

How Long Does a SASE Deployment Take?

How long a SASE deployment takes is a program duration measured from readiness assessment through SASE migration and optimization, commonly 6 to 18 months for a mixed VPN and branch estate.

SASE deployment time is driven by identity hygiene and site count.

A first wave of one user group can complete in 4 to 8 weeks after the IdP is connected.

That duration is why the next question is whether SASE should be deployed all at once or in phases.

Should SASE Be Deployed All at Once or in Phases?

No, SASE should not be deployed all at once when identity, branches, and cloud edges still share a mixed VPN estate; SASE deployment is a phased SASE rollout.

Gartner framed SASE as a multi-year architecture shift, and production SASE migration is sequenced by user group and site so a failed wave can be reversed.

A greenfield office with no legacy VPN is the exception, so SASE deployment success is still measured after each wave.

How to Measure SASE Deployment Success?

Measures of SASE deployment success are the four numeric checks that confirm a SASE architecture rollout has replaced the old path: policy coverage, path latency, VPN retirement, and change lead time.

Each measure is taken after a SASE migration wave so SASE deployment can expand, pause, or roll back on evidence rather than on a go-live date.

Policy coverage is the share of in-scope users and applications that receive SASE policy from the new engine. It tells SASE deployment whether SASE implementation still has shadow paths. A first-wave target is 100 percent of the named group, not a blended estate average.

Path latency is the median user-to-application delay with inspection enabled, compared with the pre-SASE VPN or backhaul path. It is the experience check for SASE rollout. Record it per region, because a global mean hides a failed point of presence.

VPN retirement is the count of concentrators and always-on VPN profiles that no longer carry production sessions. It is the retirement check for SASE migration. A SASE deployment that still hairpins users through the old concentrator has added a system, not replaced one.

Change lead time is the elapsed time from approved intent to published SASE policy. It is the operations check for SASE implementation. A working target is same-day publish for a standard group change, which is also how SASE Use Cases stay operable after the first wave.

Those measures only stay green if SASE deployment follows a short list of best practices, which is the final heading.

What are SASE Deployment Best Practices?

SASE deployment best practices are the four operating rules that keep a SASE architecture rollout inside identity, phases, one policy source, and a planned retirement.

Each practice is a control on SASE implementation so SASE migration does not recreate the perimeter in a new console.

Identity-first cutover is the rule that the IdP, groups, and posture signals are connected before any user traffic moves. It is the sequencing control for SASE deployment. Connecting identity first is what lets ZTNA replace VPN without encoding office subnets as trust.

Phased site migration is the rule that SASE rollout moves one user group and one site at a time in monitor-then-enforce mode. It is the blast-radius control for SASE migration. A reversed wave is cheaper than a global dual-path outage.

Single policy source is the rule that identity, inspection, and routing intent are authored once and compiled to every edge. It is the consistency control for SASE implementation. A second dialect in a leftover proxy is how SASE deployment quietly splits.

Parallel run then retire is the rule that the old VPN or proxy stays only for the current wave, then is removed when measures pass. It is the completion control for SASE deployment. Retirement is the step that turns a SASE architecture from an extra system into the path of record.

Followed in order, these practices close the SASE deployment loop from definition and model choice through steps, prerequisites, challenges, and measured SASE rollout.

Identity-centric design

Definition. Every access decision begins with a verified identity rather than a network location. The user, the device, and the session context together determine what may be reached — an IP address is evidence of nothing.

Why is it important?

  • Network position stopped correlating with trust
  • Users and applications both left the perimeter
  • Stolen credentials need a second gate

Benefits

  • Policy travels with the person
  • Access survives office, home, and travel
  • Revocation is immediate and global

How to use it

  • Consolidate identity providers first
  • Attach device posture to every claim
  • Express policy in roles, not subnets

Zenarmor's approach

Identity is resolved before the first packet is forwarded, and the resolved claim travels with the session through every subsequent inspection stage rather than being re-derived at each hop.

Testimonial

“Once identity became the anchor, half our firewall rules turned out to be describing office floor plans.”

Security architect / Financial services
02

Cloud-native framework

Definition. The service is built as elastic multi-tenant software, not as virtualised appliances. Capacity, features, and fixes are delivered continuously without a per-site upgrade project.

Why is it important?

  • Appliance refresh cycles gate security
  • Capacity planning becomes guesswork
  • Patch lag creates uneven protection

Benefits

  • New controls arrive everywhere at once
  • No firmware or maintenance windows
  • Capacity follows demand automatically

How to use it

  • Retire hardware on its natural cycle
  • Track feature parity, not box count
  • Budget as service, not capital

Zenarmor's approach

Every inspection capability ships to all tenants from the same build, so no customer runs a version that is quietly a year behind the threat landscape it is meant to address.

Testimonial

“The upgrade conversation simply disappeared from our quarterly planning.”

VP infrastructure / Logistics
03

Distributed points of presence

Definition. Inspection happens at many geographically distributed edges rather than at one or two central chokepoints, so the security control sits close to the person who triggered it.

Why is it important?

  • Backhaul adds avoidable round trips
  • Central chokepoints are single failures
  • Distance is felt by every user

Benefits

  • Shorter paths to cloud destinations
  • Regional failure stays regional
  • Consistent experience across markets

How to use it

  • Map users against edge coverage
  • Measure before and after cutover
  • Prefer nearest healthy, not nearest

Zenarmor's approach

Edge selection weighs live health alongside geographic proximity, so a congested nearby point of presence yields to a slightly more distant one that will actually serve the session faster.

Testimonial

“Our Singapore staff stopped filing tickets about the London data center.”

Network operations / Manufacturing
04

Unified security stack

Definition. Web filtering, firewall, access control, threat prevention, and data protection run as one pipeline over a single decode of the traffic, rather than as separate products chained in sequence.

Why is it important?

  • Chained products decrypt repeatedly
  • Each hop adds latency and failure
  • Context is lost between vendors

Benefits

  • One decode, many decisions
  • Shared context improves accuracy
  • Fewer integration seams to defend

How to use it

  • Verify single-pass in evaluation
  • Compare latency under full policy
  • Ask which engines share context

Zenarmor's approach

Traffic is decrypted and parsed once; every engine then reads from that shared representation, which is why enabling an additional control does not compound the latency budget.

Testimonial

“Turning on DLP used to cost us 40 milliseconds. Now it costs us a checkbox.”

Security engineering / Health technology
05

Context-aware access control

Definition. Access decisions weigh live context — device posture, location, time, sensitivity of the resource, and recent behaviour — instead of resolving a static allow list.

Why is it important?

  • Static rules age badly
  • Risk changes mid-session
  • One identity, many device states

Benefits

  • Proportionate friction for users
  • Automatic response to posture drift
  • Fewer standing exceptions

How to use it

  • Grade resources by sensitivity
  • Define step-up triggers explicitly
  • Review exceptions on a schedule

Zenarmor's approach

Context is re-evaluated during the session, not only at establishment, so a device that falls out of compliance mid-session loses access to sensitive resources without waiting for a re-authentication event.

Testimonial

“Our exception list went from four hundred entries to eleven.”

Identity lead / Global retail
06

Integrated networking and security

Definition. Routing decisions and security decisions are made by the same service with the same information, rather than by two teams operating two products that meet only at a ticket.

Why is it important?

  • Split ownership creates blind spots
  • Path choice affects enforcement
  • Incidents cross both domains

Benefits

  • One change process end to end
  • Routing respects policy intent
  • Faster joint troubleshooting

How to use it

  • Merge runbooks before tooling
  • Share on-call between teams
  • Measure experience and risk together

Zenarmor's approach

Path selection and policy enforcement consult one state model, so a route change can never silently move a session onto a path where a required control is unavailable.

Testimonial

“The network and security bridge calls became one call.”

Head of operations / Professional services
07

Global network fabric

Definition. A private backbone interconnects the points of presence, so traffic between edges rides a measured, managed network rather than taking its chances on the public internet.

Why is it important?

  • Public transit varies hour to hour
  • Long-haul jitter breaks real-time apps
  • Peering disputes affect users

Benefits

  • Predictable inter-region latency
  • Measured, not best-effort, transit
  • Deterministic failure behaviour

How to use it

  • Identify cross-region app flows
  • Test during regional peak hours
  • Compare against current MPLS spend

Zenarmor's approach

Inter-edge transit is continuously measured rather than assumed, and sessions are re-pathed when a segment degrades — before the degradation reaches the threshold a user would notice.

Testimonial

“We retired two MPLS circuits and the call quality went up.”

Network architect / Logistics
08

Application-aware routing

Definition. The service identifies the application behind a flow and routes it according to that application's actual requirements, rather than treating every packet on a port identically.

Why is it important?

  • Port numbers describe little
  • Voice and backup want opposite paths
  • Encrypted traffic hides intent

Benefits

  • Latency-sensitive apps get priority
  • Bulk transfer stops crowding calls
  • Policy expressed in app names

How to use it

  • Inventory business-critical apps
  • Set explicit path preferences
  • Validate with experience metrics

Zenarmor's approach

Application identity is derived from behavioural and metadata signals that survive encryption, so routing intent does not depend on breaking TLS where policy says it should be left intact.

Testimonial

“Backups no longer take the sales team's video calls down with them.”

Infrastructure lead / Health technology
09

Edge-based processing

Definition. The full policy decision — inspection, classification, and enforcement — is executed at the edge the user reached, not referred back to a central authority for adjudication.

Why is it important?

  • Central adjudication adds a round trip
  • Control plane outages must not block
  • Local decisions scale linearly

Benefits

  • Decisions in single-digit milliseconds
  • Edges keep enforcing when isolated
  • Throughput scales with edge count

How to use it

  • Test behaviour during partition
  • Confirm local logging and buffering
  • Check policy propagation time

Zenarmor's approach

Each edge holds a compiled copy of current policy and continues enforcing it if the control plane becomes unreachable, buffering telemetry until the connection is restored.

Testimonial

“A regional outage stopped being a security event and became a reporting delay.”

CISO / Manufacturing
10

Encrypted traffic inspection

Definition. Encrypted sessions are inspected selectively and lawfully, with explicit exclusions for categories where inspection is inappropriate, so protection does not stop at the TLS handshake.

Why is it important?

  • Nearly all threats arrive encrypted
  • Blanket decryption is unacceptable
  • Privacy law constrains inspection

Benefits

  • Threats visible inside TLS
  • Health and finance stay excluded
  • Defensible, documented exceptions

How to use it

  • Write the exclusion list first
  • Involve legal and works councils
  • Publish the policy to staff

Zenarmor's approach

Inspection scope is expressed as policy with named exclusions and a change history, so the question "who could read what, and when" has a documented answer rather than a configuration archaeology exercise.

Testimonial

“Our works council approved it because the exclusions were legible.”

Data protection officer / Financial services
11

Continuous verification

Definition. Trust is re-established throughout a session rather than granted once at authentication. A session that becomes risky is downgraded or terminated while it is still running.

Why is it important?

  • Sessions outlive their justification
  • Tokens get stolen after issue
  • Device health changes silently

Benefits

  • Shorter window for stolen sessions
  • Posture drift handled automatically
  • Step-up only when warranted

How to use it

  • Define risk signals worth acting on
  • Set proportionate responses
  • Rehearse the termination path

Zenarmor's approach

Risk is scored continuously from device, behavioural, and threat signals; crossing a threshold triggers the response the policy names, from silent logging through step-up to immediate termination.

Testimonial

“The session ended before the analyst finished reading the alert.”

SOC manager / Professional services
12

Microsegmentation

Definition. Workloads and applications are isolated from one another by policy, so that reaching one service confers no ability to reach its neighbours on the same network.

Why is it important?

  • Flat networks amplify one breach
  • Lateral movement is the real damage
  • VLAN segmentation ages poorly

Benefits

  • Blast radius bounded by design
  • Segmentation follows the workload
  • Clear service-to-service intent

How to use it

  • Map real service dependencies
  • Start in observe-only mode
  • Tighten one tier at a time

Zenarmor's approach

Segments are expressed as workload identity rather than address range, so a service that moves, scales, or is rebuilt keeps its segmentation without anyone editing a subnet table.

Testimonial

“The incident stayed inside one tier. That is the whole story.”

Head of security / Global retail
13

Single policy engine

Definition. One engine interprets one policy language for every control and every edge, removing the translation layer where most real-world security gaps are quietly introduced.

Why is it important?

  • Translation between products drifts
  • Duplicate rules contradict silently
  • Audits cannot follow four dialects

Benefits

  • One rule, enforced identically
  • Change history in one place
  • Audit evidence is a single export

How to use it

  • Rebuild intent, do not import rules
  • Delete what nothing references
  • Review policy as code

Zenarmor's approach

Policy is authored once and compiled to every enforcement point, so there is no per-product dialect in which a rule can mean something subtly different from what its author intended.

Testimonial

“We found nine rules that cancelled each other out. In one afternoon.”

Security architect / Manufacturing

Evaluating a platform

How to evaluate
a SASE platform.

A complete evaluation covers six areas, in order. Each one narrows the field before the next begins — starting with what you already run, and ending with how you would expand after the first use case succeeds.

Environment, requirements, and existing architecture

Start by defining what must be protected, then take an honest inventory of what is already deployed. Every later comparison depends on this being accurate.

What has to be protected?

Define the users, branches, cloud workloads, applications, contractors, IoT devices, and legacy systems in scope. Devices that cannot run an agent — industrial controllers, medical equipment, unmanaged sensors — deserve their own line, because they eliminate certain platforms outright.

What is already in place?

Assess existing firewalls, VPNs, SD-WAN, identity providers, endpoint tools, internet connections, and traffic flows. Knowing which of these you intend to keep and which you intend to retire converts a vague modernization project into a scoped migration.

Deployment coverage and security capabilities

Coverage and capability are separate questions. A platform can hold a strong feature list and still be unable to reach a part of your estate.

Where can it actually be deployed?

Determine whether the platform can protect endpoints, branches, cloud environments, private applications, and devices that cannot run an agent. Agentless coverage is the most common gap between a demonstration and a production rollout.

Which capabilities are genuinely present?

Evaluate next-generation firewalling, secure web access, application control, DNS security, malware protection, TLS inspection, zero trust network access, segmentation, device posture, and threat detection — and confirm which are native rather than resold or roadmapped.

Architecture, policy consistency, and data handling

This is where platforms differ most and where feature sheets say least. The question is where your traffic goes and who can see it.

Where is traffic inspected?

Understand whether traffic must be backhauled through vendor points of presence, or whether inspection can run on-premises, at the branch edge, or in infrastructure you operate. Then establish how customer data is handled: what is retained, where it is stored, who can access it, and what crosses a jurisdictional border when TLS is terminated.

Does one policy hold everywhere?

Confirm whether consistent security and access policies can be applied across users, devices, branches, gateways, and cloud workloads — or whether some of those require a second console and a separately maintained rule set.

Performance, reliability, management, and visibility

Measure under conditions that resemble production. Encrypted traffic and distance are what separate platforms, and neither appears in a lab demonstration.

What should be measured?

Test latency, throughput, application performance, tunnel stability, and failover behavior — then repeat the tests with TLS inspection enabled, since decryption is where throughput claims are typically lost.

Can the team operate it?

Review deployment simplicity, centralized management, reporting, alerting, troubleshooting, and role-based access. Managed service providers should additionally verify multi-tenancy and delegated administration before anything else on this list.

Integrations, migration, and proof of concept

A platform that does not fit the surrounding stack creates work rather than removing it. Validate the seams before committing.

What has to interoperate?

Validate integrations with identity providers, endpoint detection and response, SIEM platforms, networking infrastructure, and any other service that must exchange signal with the enforcement layer. Identity is the dependency that most often stalls a migration.

What does a real proof of concept look like?

Run one using representative users, branches, applications, devices, and policies — with success criteria defined in advance, in writing. A proof of concept without predetermined pass conditions tends to conclude with whichever result the vendor prefers.

Commercial fit, implementation, and expansion

Compare total cost of ownership rather than list price, and plan the sequence in which coverage will grow.

What belongs in the cost comparison?

Compare licensing, infrastructure costs, professional-services requirements, scalability, support, roadmap, partner capabilities, and total cost of ownership. Include the parallel-run period, when the old stack and the new platform are both live and both billed.

Where should a rollout begin?

Determine how to start with one priority use case — VPN replacement, branch security, or remote-user protection — and expand from there. A first phase that resolves a specific, visible problem earns the organizational credit that the remaining phases will need.
